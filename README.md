# RASTERFASTER composition tool

Development: two processes (to just use the app, build and install **Rasterfaster Server.app**, see [below](#rasterfaster-serverapp-api--dock-icon-opens-the-pwa)):

```bash
# 1. API (FastAPI; first time: /opt/homebrew/bin/python3.13 -m venv .venv1 && .venv1/bin/pip install -r requirements.txt): lists / serves .stl files from ~/Documents/3D/RASTERFASTER (override with RF_ROOT, PORT)
cd backend && .venv1/bin/python main.py

# 2. Angular UI (proxies /api to :8100)
cd frontend/3d-tool && npm start      # http://localhost:4200
```

Tests: `cd backend && .venv1/bin/python -m pytest`

Library code is kept apart from the document code so it can be published on its own (plan: `docs/library-catalog-plan.md`): the API is the `backend/rf_library` package (router, `ops.py`, `searchterms.py`; `main.py` mounts it), the UI is `frontend/3d-tool/src/library/`, imported as `@rasterfaster/library` (its `public-api.ts`; the API base is `RF_LIBRARY_CONFIG`). The library never imports from `src/app`, and the app never deep-imports the library: `npm run check:boundaries` checks both.

Pick up backend code changes without killing the process (re-execs in place, same PID):

```bash
curl -sS -X POST http://127.0.0.1:8100/api/runtime/restart -H 'Content-Type: application/json' -d '{"reason":"code change"}'
```

**Catalog** (button next to the Trash, bottom left of the file list): the parts catalog, a near full-screen dialog with a card for every STL of the library. Folder chips, **Find** (same syntax as the file list; `/` focuses it), sort by name, date or size; arrow keys move, Enter or double-click adds the part to the document, With Manage on the catalog changes the library too (tick boxes, Move to Trash with Undo, Rename, Duplicate, Move, new folders, and the same for a whole folder); the **CLEAN UP** row has the `_OLD` and `UNUSED` filters and **Check for doubles** (files that are exactly the same) and **Check for same shape** (a part exported again or moved in an assembly: same triangle count, size, volume, area and centre), buttons that look for them (`POST /api/catalog/duplicates/scan?mode=exact|shape`) and list the groups with actions on every copy. Esc closes; right-click a file in the file list ▸ **Open in Catalog** shows it on its page. `GET /api/catalog` lists the files.

Tree keyboard (Finder-style): ↑/↓ move, → expand / step into folder, ← collapse / go to parent, Home/End.

## Documents (assemblies)

Saved as JSON in `~/Documents/RASTERFASTER_APP` (override with `RF_DOCS`), together with the gallery (`<id>.images/`: pictures, videos and their notes) and the versions (`<id>.versions/`). The UI autosaves ~0.4 s after each edit.

```
GET    /api/documents        list   [{id, name, itemCount, modified}]
POST   /api/documents        create {name?, items?}  -> 201 + document
GET    /api/documents/{id}   read
PUT    /api/documents/{id}   replace {name, items}   (404 if it doesn't exist)
DELETE /api/documents/{id}   delete -> 204
```

## 3MF export (Bambu Studio)

```
GET /api/documents/{id}/export.3mf?bed=256
```
The **Assembly** button: the parts exactly as assembled, centred on a `bed` × `bed` mm plate; import the file in Bambu Studio and work with it there. Parts set to Do not export are left out.

The bottom of the 3D view has two info lines in the same font: on the left the document (`2 objects · 35 × 15 × 44 mm`), on the right the **selected part(s)**: the size of the selection's box, the volume of the parts and the name (`15.3 × 15.3 × 44.0 mm · 2.4 cm³ · BOLT_S8`; with several selected `35.3 × 15.3 × 44.0 mm · 4.9 cm³ · 2 selected`). Nothing selected, nothing shown; a long name is cut at the end.

A part whose file is **not in the library** (you moved its folder to the Trash, or renamed or deleted it outside the app) gets a yellow ⚠ in the parts list; hover it to read where the file went: in the Trash (and in which folder: Put Back there and the part works again) or just gone. The check is repeated whenever the library changes (trash, rename, move, Put Back). **Find in browser** on such a part says the same in the file list (“x.stl” is in the Trash, inside “folder”: put it back to find it here) with an **Open Trash** button that opens the Trash dialog.

The **parts list** in the document panel (the panel on the right: document, export, parts list, position) selects like the file list: a click selects one part, **⌘-click** adds or removes a part, **Shift-click** selects everything from the last clicked part to this one (the range keeps its anchor, so a second Shift-click changes the end of the range), **⌘⇧-click** adds that range to what is selected. The 3D view shows the same selection; the part you clicked last is the one whose position is shown.

File list: **⌥⌘⌫** deletes the selection immediately (asks first: Enter deletes, Esc cancels; not into the Trash), ⌘⌫ moves it to the Trash. Esc right after **New Folder** takes the new folder back. Esc closes an open dialog without deselecting anything.

**Shaded with light** (⌥6, the last button) shows the parts with a glossy material and smooth curved walls, lit by a key light from high above and a little behind that casts soft shadows (on the parts themselves and on the build plate); the light source is drawn as a wire model like Blender's sun: a ring with rays and a beam with an arrow head showing where it shines (left out of the SVG view). The light is saved in the document file (item `light`: `direction`, and the `target` point or the `targetId` of a part it follows), so it is where you left it when the document is opened again, in the `.rasterfaster` export too, and the Blender export uses it as its key light, a sun of strength 6 (the fill, rim and under lights are turned down to a third so it shows) shining from the light's direction at its part or point: from the saved light of the document, or from `?light=dx,dy,dz;tx,ty,tz` (the target can also be `part:<item id>` or empty for the middle of the scene) when a call brings its own. A light below the ground lights the parts from underneath, as it does in the app. **Right-click the ring** for its menu: *Point at object* lets the light follow the part under the pointer, a click keeps it and Esc puts the light back, *Reset the light* goes back to the default. **Drag the ring** to swing the light round what it points at, also below the ground grid; let go over a part and the light points at that part (a toast says which). The view cube menu has *Reset the light* for the default (it is not kept between sessions); its SVG view is the shaded picture, like Solid.

**Solid with outline** (⌥2, also in the quick look) draws the shaded parts with their visible sharp edges in dark lines on top; the SVG view of it is the shaded picture, like Solid.

**Zip all** (Export row) packs the document file, the SVG view (in the selected display mode), the SVG drawing, the Blender file and the assembly 3MF into `<name>-v<N>.zip`.

SVG view (Export row): the 3D view as an SVG in the display mode that is selected (hidden lines removed / dashed and wireframe are line drawings, solid is a picture), with the ground grid when it is on (view cube menu ▸ Ground grid). Dimmed parts are translucent in the Blender export.

Versions (the version button of the document panel): **Delete** a version, or **Delete all previous versions…** (the newest stays). The document panel folds up with the chevron in its header.

Relink: a part whose file is missing (⚠) or that only has 3MF geometry gets another library file through **Relink file…** (object menu, the ⇄ button in the parts list, or the notice of Find in browser): the file list switches to relink mode, pre-filtered with the old name, and you pick the file there.

3MF: **Import 3MF…** (document panel) makes a new document from a 3MF of this app or Bambu Studio and links each part to its library file (by path, name, then shape); parts without a library file keep the 3MF's geometry (⚠, stored in `documents/_embedded/`). Right-click a part: **Export STL** (as placed / original), **Show in assembly**. **Shift-drag** on empty space selects by rectangle. The document panel can be moved and resized.

**Set origin** (the ⌖ button at the top right of the Rotate and Move panels): handles appear on the corners and the middle of the selected part(s); the one you click becomes their origin point, kept in the document file (item field `origin`, in the part's own STL coordinates; a part without it uses the STL's own 0, 0, 0, and a part added from the library again always starts with the STL's origin). The origin point is what the Move panel measures and what its ↺ moves to 0, and what the selection turns about (instead of the middle of its box). *Use STL origin* in the banner clears it.

The **view** (camera position, target, zoom, orthographic or perspective) you leave a document in is kept in its file (item `view`, written a few seconds after the last move; not an undo step, and it does not light the version diamond) and in the browser's local storage, so the document opens like that again after a reload, also in another browser; only moves you make yourself count, the automatic fit when a document opens is not saved. The view cube's right-click menu has a **Ground** fly-out: *None*, *Grid* (the default; the grid on the ground, as before) or *Solid*, which opens a second fly-out with the colours (the app's eight and the 30 PLA colours, the same palette as the Color menu of a part: `color-palette.ts`) and puts a plane in that colour under the parts; in the Shaded view it catches the shadows. Remembered in local storage (`rasterfaster.groundMode`, `rasterfaster.groundColor`). **Fit all** (the button with a cube in a frame, left of Home, document view): zooms and moves the view so every object is in it, from the angle you have set (Home turns the view to the isometric angle instead); handy before a render or an export of the view. The **Move** panel under the Rotate panel (document view) moves the selection with − / + by its Step (100, 20, 10, 5, 1 or 0.1 mm, remembered), shows how far each axis is from where the STL file puts the part (0 = the position saved in the file) and has a ↺ per axis to go back there; the Rotate panel has the same ↺ for the rotation. **M** shows the move tool: arrows with X, Y and Z letters at the lower left corner of the selection; the corners of the selection show as yellow dots too: click one, then a corner of another part, and the selection snaps onto it (**Move to…**, also ⇧M on its own); drag an arrow (or its letter) to move the selection along that axis, snapped to the grid (20 mm in X and Y, the height levels in Z); Esc closes the tool and puts everything back, M or a new selection closes it keeping the move. In both tools **Enter** keeps the result and leaves the tool, **Esc** undoes it. Holding **Option** while turning gives fine steps, the same step as for moving (1° or 0.1°, with the green step button): on the rings of the rotate tool, on the − / + buttons of the rotate panel, with the X / Y / Z keys and with ⇧← / ⇧→. **S** shows the scale tool: square handles on the X, Y and Z axes (X, Y, Z letters), on the planes between two axes and in the middle (all three at once), drawn at the middle of the selection; the eight corners of the selection's box have orange square handles: drag one to scale evenly along X, Y and Z; drag one of the other handles to scale the selection about the middle of its footprint, with its lowest level staying where it is, in steps of 1% (**Option**: 0.1%); Enter keeps the result, Esc puts everything back. The **Scale** panel under the Move panel does the same with − / + by its Step (50, 25, 10, 5 or 1 % of the original size, remembered) for one axis or all three (XYZ), shows the scale per axis and has a ↺ to go back to the size of the STL file. The scale is kept per part in the document file (item field `scale`, along the part's own axes, applied before the rotation) and is used by every export (3MF, SVG, glTF / Blender, STL zip). **R** shows the rotate tool in the same way (rings with letters, the X, Y and Z axes drawn as red, green and blue bars with an arrow head through the pivot (the axis of the ring under the pointer lights up), a grey pivot dot in the middle of the selection, Step from the rotate panel; Esc undoes the session).

Keyboard: **Space** toggles the fly-around, **⌥1–⌥5** the view modes, **⌘0–⌘6** the view direction (home, top, bottom, front, rear, left, right). The object menu (right-click a part) has **Color ▸**; right-click empty canvas for **Paste**. `scripts/dev_stack.py` starts the API and the dev server together.

Copy / paste: ⌘C copies the selected parts, ⌘X cuts them, ⌘V pastes at the view centre (the copied group's lowest corner snaps to the nearest grid intersection, heights and spacing are kept, parts set to Center on grid are re-centered). One paste is one undo step and the pasted parts become the selection. The clipboard holds content only (file, rotation, color, dimmed/centered flags, offsets), never ids, and is kept in local storage, so it survives reloads and works across documents and tabs. The part context menu has Copy / Cut / Paste too.

Keyboard: arrows move X/Y, Shift+↑↓ / PgUp PgDn move Z, Shift+←→ turn about Z, X/Y/Z keys rotate about that axis (Shift = reverse), V dims / shows the selection, Alt = fine steps: 1 mm or 0.1 mm, chosen with the green **Move 1 mm ⌥M / Move 0.1 mm ⌥M** button in the toolbar (click it or press ⌥M to switch, remembered), Esc during a drag puts the part back, ⌘-click centres the view on the clicked point (both modes), ⌘Z/⇧⌘Z undo/redo, ⌘D duplicate, Delete removes.

## Trackpad / mouse

Two-finger scroll pans the view (the scene follows your fingers), pinch zooms towards the cursor, one-finger drag orbits. With a mouse: Option + wheel zooms, plain wheel pans.

## Object context menu

The **Color** flyout of the object menu has the app's own eight colours (the ones new parts get in turn) and a separate **PLA** section with the 30 colours of Bambu Lab PLA Basic (`pla-colors.ts`), the names in the tooltips. Right-click a part (3D view or document list): **Find in browser** shows the part's file in the file list: the folders above it open, the file is selected (blue, the list gets the keyboard focus) and scrolled to the middle of the list (the list can be scrolled a half page past its last row for that); with several parts selected it selects all their files and scrolls to the first; an active filter is cleared first. **Dim (mute)** turns it into a barely visible ghost that ignores clicks (⌘A skips it too; in the hidden-line views its own back edges are hidden, what is behind it stays visible) — handy for working on what's inside a cover. Right-click the ghost (in the 3D view, where a solid part in front takes priority) or its row in the list to bring it back. **Center on grid** is a toggle (✓ when on, ⌖ in the list): it centers the part on the grid in **all three axes**: X and Y in the middle of the nearest 20 × 20 cell, and Z with the *centre* of the part on the nearest height level of the current Grid mode (Fine, Baseplate or Coarse). A bolt that lies on its side thus gets its axis on a cell middle and on a level, a bolt that stands up keeps its height (its centre is usually on a level already). It stays centered while the part is dragged, nudged, rotated or moved up and down (⇧↑ / ⇧↓, ⇧-drag: the centre steps from level to level; Alt gives 1 mm steps, also sideways with the arrow keys or the mouse, and leaves the cell middle until the next ordinary move) — handy for bolts, nuts and spacers. Turn it off to move freely again. **Snap to grid…** is a one-time action: handles appear on the corners and side middles of the part (bottom plane), and clicking one puts that point on the nearest 20 mm grid intersection (height unchanged; Esc cancels; a part set to stay centered stops being centered). **Move to ground** drops the part so its lowest point is at z = 0, **Move to base (6 mm)** puts it on top of the 6 mm baseplate (z = 6); several parts keep their heights relative to each other. **Do not export** (toggle; a **⊘ N** button above the part list selects all such parts, next to the ◐ button for dimmed parts) marks a mock part that is not printed: it stays in the document but is left out of the 3MF and SVG exports; the BOM lists it in its own "Not exported" section (also in the CSV, without a total). **Move to…** (also ⇧M) is a two-step move: first click a corner of the selected part (handles on all 8 corners of its box), then a corner of another part (handles appear on every other part): the selection snaps so the two corners coincide. Esc cancels either pick mode, whatever has keyboard focus.

## Searching inside Fusion 360 files (f3dsearch)

Opening big cloud designs in Fusion to find one component takes ages. `scripts/f3dsearch.py` finds component and body names inside `.f3d` files without Fusion:

```
backend/.venv1/bin/pip install -r scripts/requirements-f3dsearch.txt     # once (zstandard)
backend/.venv1/bin/python scripts/f3dsearch.py index                    # the designs Fusion cached on this Mac (~/Library/Application Support/Autodesk/Autodesk Fusion 360/<id>/W.login/F)
backend/.venv1/bin/python scripts/f3dsearch.py index ~/Documents/Fusion-exports   # and a folder of exported .f3d files (remembered next time)
backend/.venv1/bin/python scripts/f3dsearch.py search ESP32 "ALT IV"    # components whose name contains every word, per design (only its newest version; --all-versions shows all)
backend/.venv1/bin/python scripts/f3dsearch.py tree RF14 --bodies --depth 2   # the hierarchy of a design (needs the sidecar the Fusion add-in writes)
backend/.venv1/bin/python scripts/f3dsearch.py list
```

The Fusion add-in writes the hierarchy of every design it saves (and of every local file it opens) as `.meta/<name>.tree.json` next to the `.f3d`: `search` then shows where a name sits (`NERO   in 14.2.NERO_BIANCO_CONTROL`) and `tree DESIGN` prints the component tree, `diff DESIGN` (or `diff RF14_v6 RF14_v7`) lists what was added, removed or moved between two versions, a design with a hierarchy file is searched by its real component and body names (`search --raw` adds every other string of the file) (`--bodies` lists the bodies, `--depth N` limits the levels).

Only designs that are on this Mac can be searched: the cache holds the designs you opened in Fusion; for the others export them (File > Export > Fusion Archive, or Download in the Data Panel) into a folder and index that. The first index reads every file (about 15 s for 6.5 GB), later runs only the new or changed ones; searching is instant. Versions and copies of one design (`RF14_v3`, `RF14 v4`, `RF14`, the cache's `_RF14`) count as one design: a search shows the newest version with a match and says how many older versions are hidden, and when an older one has matching names the newest lacks (a removed component). `search --all-versions` and `list --all-versions` show every file. A subfolder called `VERSIONS` (where the Fusion add-in can move older versions) is not searched; to search it too, give that folder to `index` once: `index ~/Documents/FUSION360/VERSIONS` (the next plain `index` drops it again). The index is `~/Library/Application Support/Rasterfaster/f3d-index.json`. The names are read as text, not with a real parser of Fusion's format.

## Fusion 360 add-in: local .f3d files (AddInRasterfasterLocalF3D)

For working without the Fusion cloud (the free Personal Use plan allows 10 active documents): `fusion-addin/AddInRasterfasterLocalF3D` adds three commands to Fusion's Utilities tab > Add-Ins panel:

- **Save Local Copy**: exports the open design into the local folder (default `~/Documents/FUSION360`). With **Add version** ticked (the default) the file is `<name>_v<N>.f3d` with N one above the highest version of that name in the folder (`RF14_v2` and `RF14 v4` are versions of `RF14`), so each save is a new file; without it the file is `<name>.f3d` and an existing one is replaced after a question. It writes a hidden temporary file first and then moves it over the old copy, so a failed export never damages the file that is there. A design opened with **Open Local File** saves back to the file it came from.
- **Open Local File**: imports a local `.f3d` as a new, unsaved document. It is not in the cloud unless you save it there; when you close it choose *Don't save*.
- **Local Folder**: picks another folder (remembered in `localf3d.json` next to the add-in).

The full install and usage guide is in [fusion-addin/README.md](fusion-addin/README.md). In short, to add it to Fusion once: Utilities > Add-Ins > Scripts and Add-Ins, click **+** (Script or add-in from device) and choose the folder `fusion-addin/AddInRasterfasterLocalF3D`; Fusion keeps working from that folder, so a change in the repo is live after you stop and run the add-in again (tick *Run on Startup* to keep it running). Do not also copy it into Fusion's AddIns folder: Fusion would list it twice. Assign keyboard shortcuts to the three commands in Fusion's preferences. Exports of big designs take a while and Fusion is busy meanwhile. After saving, run `scripts/f3dsearch.py index` to update the name index.

## Install as an app (PWA)

The production build (served by the API on http://localhost:8100 after `ng build`) is an installable PWA: manifest, icons and an Angular service worker that caches the app shell (the `/api` calls are never cached). In Chrome use *Install Rasterfaster*. When a new build is deployed an **Update** button appears in the header; click it to reload into the new version. The service worker is off in `ng serve`.

## Rasterfaster Server.app (API + Dock icon, opens the PWA)

```bash
scripts/build-app.sh               # builds dist/Rasterfaster Server.app (about 40 MB: Python, the API and the Angular app inside) and copies it to /Applications (replacing an older Rasterfaster.app / Rasterfaster Server.app)
scripts/build-app.sh --no-install  # ... only builds it
```

Click **Rasterfaster Server**: it starts the API (which also serves the web app on http://localhost:8100/) and opens the installed **Rasterfaster PWA**; it has no Dock icon of its own while the PWA is its window. **Closing the PWA window (or quitting the PWA) stops the API** a few seconds later and the server app ends too, so the backend only runs while you use the app. The PWA is the real Chrome app, so browser storage (sort order, filter, panel width, last mode), copy/paste, the dev tools and updates all work as in Chrome. Clicking "Rasterfaster Server" again while it runs just brings the PWA forward. Pin "Rasterfaster Server" to the Dock (or find it in Launchpad / Spotlight) as the one icon to click; the PWA's own icon alone does not start a backend (you would see the red offline banner).

One-time setup: install the PWA from the *production* address: start the server app, open http://localhost:8100/ in Chrome and use *Install Rasterfaster* (uninstall the old one that was installed from http://localhost:4200/ first; that is the `ng serve` dev address). Without an installed PWA the server app opens http://localhost:8100/ in Chrome instead and keeps a Dock icon (Quit stops the API); it also keeps its Dock icon if the PWA never shows up within a minute. After a new build the PWA shows the "Update available" button.

Paths in the packaged app (`backend/appconfig.py`): documents, images, videos and notes in `~/Documents/RASTERFASTER_APP` (the documents that exist at build time are copied there on the first run when the folder does not exist yet, nothing is overwritten), the STL library from `config.json` in `~/Library/Application Support/Rasterfaster` (`libraryRoot`, default `~/Documents/3D/RASTERFASTER`), `RF_ROOT` / `RF_DOCS` / `RF_FRONTEND` / `PORT` still override. If an API already answers on port 8100 (for example `python main.py`), the app uses that one and does not start a second; if something else holds the port it picks a free one (the PWA then has a different address). The app is unsigned: the first time, open it with right-click > Open. Blender export needs Blender installed (found at /Applications/Blender.app).

Development is unchanged: `cd backend && .venv1/bin/python main.py` and `cd frontend/3d-tool && npm start -- --open`. The build uses its own `backend/.venv-app` (PyInstaller and the macOS Cocoa bindings, see `backend/requirements-app.txt`). `python app.py` (in that venv) runs the same server app without packaging. If the STL library folder does not exist on another machine, put its path in `~/Library/Application Support/Rasterfaster/config.json` as `{"libraryRoot": "/path"}`.

### Shipping a change (the flow)

1. Develop with the two dev processes above (backend changes: `POST /api/runtime/restart` re-execs the running API in place).
2. Test: `cd backend && .venv1/bin/python -m pytest` and `cd frontend/3d-tool && npm test`.
3. Bump the version and write the changelog: `cd frontend/3d-tool && npm run bump:version -- X.Y.Z` (updates `package.json`, `src/app/build-info.ts` and the service worker's `appData.version`, so the PWA's update button shows the new number) and add a dated entry to `CHANGELOG.md` (FE / BE bullets with file paths).
4. Build and install the app: `scripts/build-app.sh` (builds the Angular app, the icon and `dist/Rasterfaster Server.app`, copies it to /Applications). Restart the API you have running so it has the new backend code (`POST /api/runtime/restart`), because an old API ignores new endpoints.
5. Open the app: click **Rasterfaster Server**; the PWA shows the green **Update available vX.Y.Z · reload** button within a minute; click it.
6. Commit and push to `main`.

## Groups, saved views, the image library and Design / Render mode

**Groups.** ⌘G (or *Group* in the part menu) gathers the selected parts, ⌘⇧G (*Ungroup*) dissolves the group; one level, saved with the document (item field `groupId`, document field `groups`). A group is selected, moved, turned, scaled and coloured as one; the part list shows a group row (count, ▾ fold, double-click renames) with its members indented. In the 3D view a click selects the whole group and a second click one part; in the list only the group's row selects the whole group, a click on a member selects that member. A right-click on a part that is not selected opens the menu for that part alone.

**Saved views.** The floating **Views** panel (movable, collapsible, with a help text) saves the camera, display mode, Design / Render mode, light direction and ground / grid options under a name (document field `views`, also in versions and the document file). Click a view to go there (the camera glides), double-click its name to rename it in place, ⟳ replaces it by what you see now, ✕ deletes it; keys **1 – 9** go to the first nine views, **⇧1 – ⇧9** replace them; the view the camera is on is highlighted.

**Gallery.** (Formerly the image library.) The floating **Gallery** panel (**I** key or the *Images* button; movable, resizable, collapsible) keeps the pictures and videos of the document in `documents/<id>.images/` (**Add file…** or a drop puts a PNG or MP4 of your own in it): finished full-size renders arrive by themselves, *Save quick render to library* in the Render dialog keeps a quick render. Every picture carries the document version it was made from (`v13`, `v13*` when the working copy was ahead) and the render settings (camera, depth of field and focus part, ambient, lamp, colours, crop). A picture also keeps the view it was made from: *Go to view* brings that camera, display, light and ground back to carry on working, *Save as view* adds it to the Views panel. Click one to view it large (← → or the arrows cycle through them), download it, rename it or delete it; *Render HD ▾* renders it again at full size with the same camera, light and settings; a right-click menu has the same actions; *Clean up* deletes the pictures of older versions or the quick renders in one go. API: `GET/POST /api/documents/{id}/images`, `GET …/images/{imageId}.png`, `PUT/GET …/images/{imageId}/thumb.jpg`, `PATCH` and `DELETE …/images/{imageId}`, `DELETE …/images?beforeVersion=&kind=`.

**Turntable direction and view cube arrows.** The turntable goes round CCW or CW (play button's menu, Render dialog). The arrows round the view cube step to the next face or turn the view 45° about the vertical axis. The light lights up on hover, its menu can point it at the objects' centre and says what it points at. Design and Render mode keep their own camera mode.

**FX styles.** The FX dropdown (toolbar in Render mode, and the Render dialog) gives renders a style: Cartoon, Outline, Sketch, Clay, Blueprint, Isometric, X-ray, Low poly, Wireframe, Thermal, Clay rough, Clay rough colour or Cut-away, Hidden lines, Depth fog, Low fog, Watercolour, Watercolour intense or Watercolour with ink (None is the normal render; Cut-away cuts the assembly along an axis, set in the Render dialog). Mirror parts reflect the scene in the 3D view too: flat ones exactly, other shapes approximately. API: `fx=none|cartoon|outline|sketch|clay|blueprint|isometric|xray|lowpoly|wireframe|thermal|cutaway|clayrough|clayroughcolour`, `cut=z:50:0` (plus `hiddenlines|fog|lowfog|watercolour|watercolourintense|watercolourink`). Thermal is hottest at the focused part, else at the part the lamp points at.

**Picture frame.** In Render mode the toolbar has the shape of the picture (the same setting as the Render dialog), **Frame** (a dashed frame over the view: exactly what the render contains; a thin cross marks the middle of the objects, click it to centre the view) and **Box** (an outline round all the objects); the **Render** button (F12, fn + F12 on a Mac) opens the dialog. Reflects also has *None*, the depth of field can focus on the centre of the objects, the Views panel shows slots 1 – 9 and Rotate, Move and Scale are one *Transform* panel.

**Reflections.** The *Reflects* menu in the Lighting row sets what metal, mirror and glass reflect: Studio dark (the default), Softbox, Daylight or Neutral grey, in renders and in the 3D view; the background stays as it is. Shapes other than 16:9 zoom so the parts fill the picture. API: `reflections=0..3`.

**Turntable video.** The Render dialog's *Turntable video* row renders an MP4 of one turn through the render queue: *Camera circles* or *Objects turn* (the same way round), *One turn takes* 3, 5, 10 or 30 seconds, quality *Draft* (960 px, 12 samples, 24 fps: a few minutes), *Standard* or *Fine*, with a time estimate; the width follows the size menu (4K at most) and the shape menu. **Quick video** makes a small one at once and shows it in the dialog; **Quick draft video** is a tiny, rough one (320 px, 12 fps) in seconds. *Track* (or *Pick…*, or *Track an object…* in the play button's menu) chooses the part to track. Two settings say what the camera does: **Goes round** (Camera circles): all objects (the middle of the parts, the default), the view (the point you look at) or the tracked part; **Looks at** (Camera circles and Objects turn): as the view does (the camera keeps its angle), all objects or the tracked part (kept in the middle of the picture, like a drone filming its subject; with Objects turn the camera stays where the view is). The play button above the view cube opens a menu with a **live preview** of the turntable in the 3D view (you can steer meanwhile; Space pauses, Esc ends). A video is kept in the Gallery with a thumbnail and plays and loops in the viewer. API: `turntable`, `seconds`, `fps`, `track` on `POST /api/documents/{id}/render-jobs`, `GET /api/render-jobs/{id}/video.mp4`, `GET /api/documents/{id}/render.mp4`, `GET /api/render-estimate`.

**Design and Render mode.** The **Design | Render** buttons at the start of the toolbar (and the **Tab** key; Tab never moves the focus around in this app) switch the 3D view. *Design* shows every part in its own colour; *Render* shows how the picture will look: each part's own render colour and finish, hidden parts left out, and the studio's dark background and ground (or the colours chosen in the Render dialog). A part has an optional `render` field (`color`, `finish`, `hidden`): in Render mode the Color menu sets the render colour (with *Reset to the design colour* and *Copy the design colour*), the *Finish* row sets Satin (the plain PLA look), Metal, Transparent or Mirror, and *Hide in Render mode* leaves the part out. A part without a render colour keeps its design colour. Quick renders, full-size renders and the Blender file always use the render colours, finishes and hidden parts; the 3MF, SVG and BOM keep the design colours. **Do not render** stays a separate flag (kept in the scene, not drawn). Render mode has the one display mode, *Shaded with light* (⌥6), where Design mode has six; a part with the Transparent finish lets the light of the lamps through (in the view and in renders). Metal, Mirror and Transparent parts are smooth-shaded by angle (35°) in renders so their reflections are smooth; the **Quality** menu of the Render dialog sets the samples of a full-size render (96, 256 or 512). The *Finish* row also has **PEI** (Textured PEI: the sparkly powder-coat grain of a print plate in renders, in the part's render colour). Full-size renders are **queued**: one runs at a time, the others wait (at most 10 together, `RASTERFASTER_RENDER_QUEUE_MAX`), the progress message shows how many wait and has *Cancel* and *Cancel all*; every finished render goes into the image library. The Render dialog's **Shape** menu (16:9, 1:1, 4:5, 9:16; the size menu is the width) and **Transparent** checkbox (no background, the ground's shadows stay; API `aspect`, `transparent`) shape the picture. The right-click menu of the light has *Type of light* (Spot, Direct, Soft, Diffuse, Flood).

## Document versions (v1, v2, ...)

Like Fusion 360: the document is autosaved as ever (the working copy), and a **version** is a numbered, immutable snapshot of it. The pill next to the document name shows the newest version (`v3`), with a dot (`v3 •`) while the working copy has changes since; **⌘S** saves a new version (nothing is created when nothing changed), and clicking the pill opens the versions list: **View** shows an older version read-only (a blue bar says so; edits are off), **Promote** makes it the working copy again and saves it as the newest version (older versions are never rewritten), and **Back to the working copy** leaves the old version. Versions live next to the document as `documents/<id>.versions/v1.json`, `v2.json`, ... (deleted with the document). API: `GET/POST /api/documents/{id}/versions`, `GET /api/documents/{id}/versions/{n}`, `POST /api/documents/{id}/versions/{n}/promote`; a document now also reports `version` and `changedSinceVersion`.

## Saving a document as a file and restoring it

In the document panel, **Document file → Save file** downloads the open document as `<name>-v<n>.rasterfaster.json` (`v<n>` is the newest saved version, `-edited` is added when the working copy has changes since it, and there is no suffix before the first version): the parts and everything about them (colour, position, rotation, dimmed, centered, do-not-export) plus **all its versions**. **Open file…** restores such a file: a document that does not exist (any more) comes back exactly as it was, with the same id, its version history and its working copy, and is opened; if a document with that id exists you choose **Replace it** (working copy and history become the file's), **Import as a copy** (new id, the existing one stays) or Cancel. Other windows pick the restored or replaced document up through the normal sync (up to 5 s). API: `GET /api/documents/{id}/export.rasterfaster`, `POST /api/documents/import[?onConflict=replace|copy]` (409 when the id exists and no choice was given; 422 for files that are not documents). The library STL files themselves are not in the file: they are found by their library path.

## Two windows on the same document

The app polls `/api/health` every 5 s; it carries the newest modification time of any document. When that changes, a window checks whether the open document was saved by another window (the dev app on :4200 and the PWA on :8100 share the same API and documents): without unsaved edits it reloads silently ("Updated from another window"); with unsaved edits it shows an orange banner: **Load the other version** (drops your unsaved edits) or **Keep mine (overwrite)**. Saves send the `modified` time they are based on (`PUT /api/documents/{id}?baseModified=...`) and the API answers **409** with the current document when it is older, so a stale window can never silently overwrite a newer save. Without `baseModified` the API still overwrites, as before. The delay is up to 5 s.

## Offline detection and versions

The app polls `GET /api/health` every 5 s (and when the browser reports a network change). After two failed checks a red **Offline** banner appears at the bottom of the view; when the API answers again it disappears and the file list reloads. The document recovers too: if the app was started while the API was down, the document loads as soon as the API answers; edits made while it was down are saved again (they are never replaced by what is on disk). The installed PWA keeps working with its cached shell while the API is down, but nothing is saved. The version (`package.json`, shown as `vX.Y.Z` in the panel header and on the **Update available** button) is bumped with `npm run bump:version -- X.Y.Z` in `frontend/3d-tool`; that also rewrites `src/app/build-info.ts` and `ngsw-config.json` (`appData.version`). Bump it, add a CHANGELOG entry and rebuild whenever you ship a change you want installed PWAs to pick up.

## Renaming library files and directories (file management, phase 1)

Right-click a row in the file list → **Rename…**, press **Enter** (or F2) on a focused row, or click a row that is already selected, wait a moment and the name becomes editable (a slow second click, like in the Finder; a double-click still adds a file to the document, and a folder's arrow still opens and closes it): the row becomes a text field (a file without its `.stl`, which is added again); Enter again without typing or Esc cancels, Enter after typing saves; a name that is empty, starts with a dot, contains `/ \ :` or already exists is refused with the reason shown under the field. The API is `POST /api/library/rename` (`{path, newName}`, `?dryRun=true` only reports what would happen), implemented in `backend/rf_library/ops.py`.

- **Backup of the original, the first time only:** the first time a *file* is renamed, a copy of the original goes to the backup folder with the same hierarchy: renaming `<library>/1.4.BOLTS & NUTS/old name.stl` keeps `3D_BACKUP/RASTERFASTER/1.4.BOLTS & NUTS/old name.stl` (the folder is named like the library folder). If the copy fails, nothing is renamed. Renaming the same file again (A, B, C) is not backed up again: a registry follows the file (`<backup folder>/.rasterfaster/registry.json`). A backup never overwrites another one (`name (2).stl`).
- **Directories:** renaming a directory copies nothing; it is only logged.
- **Documents follow:** every part in `documents/*.json` and in their versions that points at the renamed file (or below the renamed directory) gets the new path; a part label that still equals the old file name becomes the new name (your own labels stay). Open windows reload through the two-window sync.
- **Log:** every rename is recorded in `<backup folder>/.rasterfaster/log.json` (pending first, then done, or failed).
- **Backup folder:** default `/Users/hanskerkhof/Documents/3D_BACKUP` (`~/Documents/3D_BACKUP`); change it with `RF_BACKUP` or `backupRoot` in `~/Library/Application Support/Rasterfaster/config.json`.
- Plan for the next phases (move, batch rename, tags, insight, import, backup browser): `docs/file-management-plan.md`.

### Selecting several items (file management, phase 2a)

Like in the Finder: a plain click selects one row; **⌘-click** adds or removes a row; **Shift-click** selects everything from the last clicked row to this one; **Shift+↑/↓** grows or shrinks the selection; **⌘A** selects all visible rows; **Esc** goes back to the focused row alone. A selected folder swallows the selected things inside it (an action acts on the folder only). **Move to Trash** (menu or ⌘⌫) acts on the whole selection as one action: one question at most (when documents use any of it), one **Undo** that puts everything back, and the items are stored in the Trash under one batch id. Right-clicking inside the selection keeps it (the menu then says "Move N Items to Trash" and Rename is greyed out); Rename needs exactly one row (Enter or F2 with several selected says so). API: `POST /api/library/trash-batch` (`{paths}`, `?dryRun=true` sums the documents that use them; everything is checked before anything moves).

### The Trash (delete, like the Finder)

Right-click a row → **Move to Trash**, or **⌘⌫** on a focused row (a file or a directory): no question is asked, the row goes to the Trash and an **Undo** bar (10 seconds) offers to put it back. When documents use it, you are asked first: those parts keep their path and show as missing until the file is put back (documents are not rewritten). The **🗑 Trash** button under the file list (with the number of items) opens the Trash: **Put Back** (a directory comes back whole, missing folders are made again; if something sits in the old place you can put it back as `name (restored).stl`), **Put Back All** (everything, the oldest first; a place that is taken gets `(restored)` in the name; it sits before Empty Trash), **Delete Immediately** and **Empty Trash…** (both remove for good, Empty asks once more). The Trash lives in the backup folder as `_TRASH/<id>/<name>` with an index in `.rasterfaster/trash.json` (original place, time, size, the registry entries of renamed files so they stay registered); everything is in the log (`trash-file`, `trash-directory`, `put-back`, `delete-immediately`, `empty-trash`). API: `POST /api/library/trash` (`{path}`, `?dryRun=true` lists the documents that use it), `GET /api/library/trash`, `POST /api/library/trash/{id}/put-back[?onConflict=rename]`, `DELETE /api/library/trash/{id}`, `DELETE /api/library/trash`.

An STL that is overwritten on disk shows up after a reload: `/api/file` is sent with `Cache-Control: no-cache` and the app loads STLs with fetch's `no-cache`, so the browser revalidates the ETag every time. The file list's reload button spins for at least 1 second.

## Looking at a library file

There is one view: the document. Click a file in the tree to select it, press **Space** for a quick look (a floating, resizable preview: drag the bottom-right corner, the size is remembered; switch between Solid, Wireframe, Hidden removed and Hidden dashed, remembered), and add it to the document with ⌘↓, the context menu's **Add to Document** or a double-click (with several files selected, ⌘↓, the button and the menu add all of them at once) (Enter renames, see below; drag the selection onto a folder to move it, and the right-click menu also has New Folder, Duplicate, Reveal in Finder, Copy Path and Copy Relative Path; the folder button in the header row makes a new folder at the top level, and a new folder made while a filter is active clears the filter so that it shows); adding a part (any of these ways) closes the quick look. ↑ ↓ browse files while it is open.

## File list

⌘B or the icon in the RASTERFASTER header hides and shows the panel (it slides, and the choice is remembered). Drag the right edge of the panel to resize it (double-click resets, ← → with the handle focused); the width is remembered.

**The filter box** takes several words: `PANEL S2` shows the files and folders whose name contains **any** of them (case does not matter; every word is highlighted in the list). The small **any / all** button inside the box switches to **all**: a name must then contain every word (remembered). `"PANEL MOUNT"` in quotes is one term (a phrase), and `-copy` leaves out names that contain it (`panel -glue`, `-"old part"`). A lone `-` while you type counts for nothing. The search looks at the name of each file and folder (not the whole path). When you clear the filter (✕, Esc, or by deleting the text) while a file or folder is selected, the list goes back to the whole library with that branch open: the folders above the selection are expanded, and the file (or folder) stays selected, focused and in view (blue: with ✕ or Esc the keyboard focus goes to the list, so arrows and ⏎ work at once; deleting the text by hand leaves the focus in the filter box, and the row is grey until you click in the list); this also works for the file that is open in the app when the filter text had already hidden it.

The reload button (⟳ next to Sort) re-reads the library from disk: the root and every open folder, and the search when a filter is active. The filter text is remembered across reloads.

## Silhouette edges (hidden-line views)

In *Hidden lines removed* and *Hidden lines dashed* (main view, quick look and dimmed parts) the sharp edges of a part are drawn, plus, since 0.6.0, the **contour of its smooth walls**: a cylinder, a cone or a tapered foot used to show only its top and bottom rings, because an edge was only drawn where two triangles meet at more than 25°. Silhouette edges (`silhouette.ts`) are the smooth edges between 0.5° and 25°, drawn by a small shader only where one of the two triangles faces the camera and the other faces away, so the contour follows the camera (both camera types). Switch it on or off in the view cube's right-click menu (**Silhouette edges**, remembered, default on) to compare; the hidden contour in *Hidden lines dashed* is drawn solid in the dashed colour. Flat parts (boxes) look the same either way. To remove the feature: delete `silhouette.ts` and its spec and the `silhouette` lines in `model-render.ts`, `document-scene.ts`, `quick-look.ts` and `stl-viewer.ts`.

## Camera

Right-click the view cube → **Camera**: Orthographic (default), Perspective, or Perspective with ortho faces (orthographic only while looking straight at a face of the cube, like Fusion 360). Remembered across reloads.

## Fly-around

The ▶ button next to Home (document view only; also in the view cube's right-click menu) starts a slow camera flight around the assembly: about one turn per 70 s, with the camera rising and falling, breathing in and out, and its centre drifting, so over time the assembly is shown from the sides, the top and a low angle. Zooming (scroll, pinch) keeps working while flying, so you can zoom out to see the path and back in; the 🔍 button next to ⏸ resets the zoom to the flight's default. Dragging the view or pressing ⏸ stops it. **Show camera path** (view cube right-click menu, remembered) draws the path as an amber line around the assembly, with a Blender-style camera outline at the camera's current spot on it: the whole closed loop (the flight repeats every 280 s), otherwise a preview from the current view direction. Zoom out to see it.

## 3D grid

Right-click the view cube → **3D grid** switches the ground grid to a full lattice: horizontal 20 mm grids at every height level (0, 2, 6, 10, …) up to just above the parts, plus vertical lines through every node. The choice is remembered.

## Rotating around the selection

With parts selected, rotating the view (dragging empty space, or dragging/clicking the view cube) pivots around the centre of the selection: the view glides to centre it first. Right-click the view cube → **Rotate around selection** turns this on or off (default on, remembered).

## Height grid (grid mode)

X/Y snap to 20 mm. Height snaps to levels that depend on the **Grid mode** (right-click the view cube → Grid mode, remembered):

- **Fine: every 2 mm** — 0, 2, 4, 6, 8 … (for 2 mm thick parts)
- **Baseplate: 2 mm, then 4 mm** — 0, 2, 6, 10, 14 … (default; the top of a 6 mm baseplate is a level)
- **Coarse: every 4 mm** — 0, 4, 8, 12 …

Shift+↑↓ / PgUp PgDn move the selection one level (the lowest selected part decides, the rest keeps its offsets) and Shift+drag snaps to the nearest level; Alt gives 1 mm steps. The 3D grid follows the mode. Modes are defined in `frontend/3d-tool/src/app/z-levels.ts`.

## Work area

Parts added from the file list go to the position saved in their STL (so a set exported from one Fusion assembly comes back in place); parts with similar names get the same colour.

Parts stay inside a 100 × 100 cell area (±1000 mm in X/Y, −200…2500 mm in Z); drags, keys, rotations and typed values are clamped to it, and the grid never draws beyond it. Documents with corrupt or out-of-range positions are repaired when opened.

## Blender export

**Render** in the document panel (or the key **F12**, like in Blender) opens a quick picture of how Blender renders the scene (API: `GET /api/documents/{id}/render.png`, optional `width` 160–1920, default 800, `samples` 1–128, default 24, and the same `view`, `light` and `colours` as the Blender export): the API runs Blender in the background with Cycles and the studio setup, with the camera of the 3D view, the document colours and the light of the document; about 5–20 seconds. The **Crop** checkbox of the dialog (remembered in local storage and in the document file as `render.crop`; API `crop=true` on `render.png` and `render-jobs`) makes the picture only as wide as the parts: the height stays (450 px for the quick render, 1080 px for HD) and with it the framing of the view, the width follows what is in the picture with a little room on each side (never wider than the normal 16:9 picture), and the parts are centred; so a tall stack gives a narrow picture and a row of parts a wide one. The **Depth of field** checkbox of the dialog (remembered in local storage and in the document file as `render.depthOfField`; API: `dof=true` on `render.png`, `render-jobs` and `export.blend`) puts a real depth of field into the Blender scene. Choose what is sharp with the *Focus* menu next to it (or the *Selected* button for the part selected in the document; the *Blur* menu sets the strength with five presets, **Subtle, Soft, Medium, Strong, Extreme** (`strength=1…5`, remembered in local storage and in the document file as `render.dofStrength`): the lens opening is worked out from the size of what is in the picture (its real extent, not the centres of the parts), so that something about a quarter to 0.6 of that size in front of or behind the focus is blurred by 0.3%, 0.6%, 1.2% (Medium, the default: unsharp but still recognizable), 2.5% or 5% of the picture width; remembered per document in local storage and in the document file as `render.focusId`; API `focus=<item id>`); on *nearest in the picture* it is the part nearest to the camera whose middle is in the picture; the lens opening follows the distance, so a big scene is blurred about as much as a small one (an orthographic camera has none). The **Ambient** menu (None, *Soft glow, Overcast, Softbox, Daylight, Bright studio*; remembered in local storage and in the document file as `render.ambient`; API `ambient=0…5` on `render.png`, `render-jobs` and `export.blend`) adds a big soft light above the scene and lightens the world, so shadows are no longer black (the *Lighting* row also has a **Lamp** type menu, *Spot, Direct, Soft, Diffuse, Flood*, from razor-sharp to very soft shadows: the sun's angle 0.5°, 3°, 10°, 25°, 60°; API `beam=0…4`, document field `render.beam`; and **Background** and **Ground** colour buttons for the colour behind the parts and of the round ground, with *Studio default* to go back; API `bg` and `floor`, document fields `render.background` and `render.ground`; the camera's film-like colour curve shifts the colours somewhat) (the *Lighting* row of the dialog also has a **Lamp** slider for the strength of the lamp pointed at the parts, the light placed in the document: two thirds of the way is the normal strength, shown as 100 %, every 10 steps double or halve it, from 6 % to 400 %; remembered in local storage and in the document file as `render.lamp`; API `lamp=0…60`); a tiny test render first sets the exposure so the brightest areas of a closed scene (a box around the parts) are not burnt out. The dialog has *Quick render*, *Download PNG* and **Render HD** with a size menu next to it (1920 × 1080 Full HD, the default, 2560 QHD, 3200 QHD+, 3840 4K UHD, 5120 5K or 7680 8K UHD, remembered in local storage; API `width` up to 7680): a 96 sample render that runs in the background (about a minute and a half for a small scene; API: `POST /api/documents/{id}/render-jobs`, one at a time, then `GET /api/render-jobs/{id}` and `…/image.png`, `DELETE` to cancel). The Render button then shows a spinner and is disabled, a toast says it started, a progress toast stays at the bottom while it runs (percentage, time so far, an estimate of the time left once two progress reports are in, and a **Cancel** button that stops Blender), and when it is done a message *Render of … is ready: click to view* appears and opens the picture. The page hears about it over the WebSocket `/api/ws` (needs the `websockets` package; the dev server's proxy needs a restart to pass it on: `"ws": true` in `proxy.conf.json`) and falls back to polling `GET /api/render-jobs/latest` when that is not open; a page opened later still learns that a render is ready. **Blender** in the document panel downloads a native `.blend` (API: `GET /api/documents/{id}/export.blend`); double-click it to open it in Blender. The API makes it by running Blender in the background, so Blender must be installed on the machine that runs the API (found automatically at `/Applications/Blender.app` or on the PATH; set `BLENDER` to its path otherwise; without it the button reports "Blender was not found"). You get one object per part (named like the part, in the colour of the part in the document, with the same satin finish and thin glossy coat; add `?colours=false` to the API call for all parts in one satin **Black PLA** material instead; flat shaded) exactly as placed in the document, Z up, in metres (a 20 mm cell is 0.02 m); parts marked **Do not export** are left out. The `.blend` also has a **studio setup** so a render works straight away: a dark matte floor (solid from above, invisible from below, so a camera under the ground sees through it), a dark gradient world and four area lights (warm key, cool fill, magenta rim, and a soft cool light from below), Cycles with 96 samples, AgX colour (add `?studio=false` to leave it out). The scene camera, **App view camera**, sits where the 3D view is when you press the button (same direction, centre and zoom; orthographic or perspective like the view, including the narrower field of view of a zoomed-in perspective view, so the perspective looks the same; the picture is 16:9 with the same visible height, so the sides may show more or less than the app's window). Without a view (a plain API call) it is the isometric Home view with the whole assembly in frame; pass `?view=dx,dy,dz;tx,ty,tz;height;persp|ortho[;fov]` (direction centre to camera, centre in mm, visible height in mm, vertical field of view in degrees for `persp`, default 35) to place it yourself. There is no camera animation or camera path in the export. Checked with Blender 5.0.

The same scene as glTF, without needing Blender: `GET /api/documents/{id}/export.glb` (add `?camera=false` for parts only); import it with *File > Import > glTF 2.0*.
